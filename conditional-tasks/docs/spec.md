# conditional-tasks — Спека

Эталонная игра класса B на форме `two-outcome`. Донор кладёт USDC в **один** эскроу и прикладывает текст
задания; получатель видит текст приватно, решает брать; взял (`accept`) — текст раскрыт публично; заявил
«готово» (`ready`) — окно голосования весом книги; подтвердили → деньги через сплиттер получателю +
репутация **донору**, иначе возврат донору. **Одна область = одно задание = один эскроу (`B=1`).**

Общие инварианты — `crown-spec/docs/games-harness.md`; здесь — вся специфика задания, дословно, чтобы
имплементация не требовала догадок.

## Область, идентификатор, резолвер

- **Область = задание**, ключ `scope_id = task_id` — **свободный** id (не адрес эскроу):
  ```
  task_id = sha256( "crown:conditional-tasks"
                  ‖ u8(len(canister_id)) ‖ canister_id
                  ‖ donor(32) ‖ recipient(32)
                  ‖ u64le(gross) ‖ i64le(deadline)
                  ‖ u16le(fee_bps) ‖ fee_wallet(32) ‖ u64le(nonce)
                  ‖ u64le(duration) ‖ u64le(voting_period) )
  ```
  То есть входы соли эскроу **минус `resolver`** + `canister_id` + тайминги. `task_id` коммитит `gross`
  и `deadline` (1:1: одна область — один эскроу).
- **Резолвер** = `key([task_id])` (threshold Ed25519, path `[task_id]`; локальная деривация из
  кешированного мастер-ключа, `get_resolver` — `query`).
- **Адрес эскроу** = `crown_derive::solana_pda_address(factory, [b"escrow", salt]).0`, где
  `salt = crown_salt::two_outcome(donor, recipient, gross, deadline, resolver, fee_bps, fee_wallet, nonce)`;
  `fee_bps`/`fee_wallet` — **из конфига, не из аргументов** (харнесс §9): и в `task_id`, и в соль
  канистра подставляет свои константы. Иная комиссия → другой `task_id` и другой адрес → `TaskIdMismatch`.
  `deadline` вне `i64` → `DeadlineOverflow`; все адреса ровно 32 байта иначе `BadFieldLength`.
- Круга нет: `task_id → resolver → адрес`. `text_hash` в `task_id` не входит — его несёт вызывающий и
  подпись донора (Register), канистра хранит только хеш.

## Состояния (`logic/`)

```
Created → { Accepted | Decided{Cancel} } ;  Accepted → { Decided{Cancel} | Voting } ;
Voting{started_at} → Decided{outcome} ;      Decided — поглощающее
outcome ∈ { Settle, Cancel }
```
`Created` — текст виден только получателю. `Accepted` — текст раскрыт публично. `Voting{started_at}` —
окно голосования. `Decided{outcome}` — терминал.

## Таблица переходов (полная, `logic/`)

`step(task, action, now)` сначала применяет **накопившиеся временные переходы** (`advance`), затем
действие. Временной переход персистится, даже если действие отвергнуто (провал действия ≡ `Tick`).
`match` исчерпывающий, без `_ =>`.

**Временные (`advance`), тайминги — §Тайминги:**
- `Created`/`Accepted`, `now ≥ cutoff` → `Decided{Cancel}`.
- `Voting`, `now ≥ voting_end` → `Decided{ verdict(votes) }`.
- Арифметика точки — `checked`; непредставима в `i64` → `Overflow` (состояние не меняется).
- `Decided` — неизменно.

**Действия:**

| Состояние × Действие | Результат |
|---|---|
| `Created` × `Accept` | → `Accepted` (текст раскрыт) |
| `Created` × `Decline` | → `Decided{Cancel}` |
| `Accepted` × `Decline` | → `Decided{Cancel}` (досрочно освобождает деньги донора) |
| `Accepted` × `Ready` | → `Voting{started_at: now}` |
| `Voting` × `Vote(v)` | `v.weight < MIN_VOTE_WEIGHT` → `WeightBelowThreshold`; `v.voter` уже голосовал → `DuplicateVoter`; иначе `votes.push(v)` |
| любое × `Tick` | только временные переходы |
| `Created` × {`Ready`,`Vote`} | `InvalidTransition` |
| `Accepted` × {`Accept`,`Vote`} | `InvalidTransition` |
| `Voting` × {`Accept`,`Decline`,`Ready`} | `InvalidTransition` |
| `Decided` × {`Accept`,`Decline`,`Ready`,`Vote`} | `InvalidTransition` |

Ошибки шага: `InvalidTransition · WeightBelowThreshold · DuplicateVoter · Overflow`.

## Правило вердикта (дословно)

`Cancel` ⇔ `Σвес(not_done)` **строго** больше `Σвес(done)`. Иначе `Settle`, включая: **ничью**
(`Σdone == Σnot_done`) и **пустое голосование**. Единственное исключение — **переполнение** суммирования
весов (`checked_add`): оно немедленно `Cancel`, потому что это отказ подсчёта, а не вердикт голосующих, и
`Settle` на нём позволил бы подобранными весами вынудить выплату. **Кворума нет.** Подсчёт тотален:
задание всегда финализируется в `Decided`, не застревает в `Voting`.

**Отсюда — кто чем рискует, и это надо знать, а не выводить.** Умолчание — **в пользу получателя**:
молчание голосующих есть `Settle`, работа считается принятой. Риск лежит на **доноре** — чтобы отменить
оплату, он обязан прийти сам и привести вес «не сделано», строго больший веса «сделано». Кворума нет, так
что цена одного голоса прежняя (`MIN_VOTE_WEIGHT = $0.10` репутации у этого получателя, покупаемой прямым
донатом себе на второй кошелёк за оборот суммы плюс `INGEST_PRICE` ≈ $0.023, `00 §10.1`), но теперь она —
цена **отмены**, а не цена принятия: при пустом голосовании один голос «не сделано» за ~$0.12 останавливает
выплату, а при равном весе не останавливает. Симметрично прежнему перекосу, только в другую сторону.

**Голосование здесь социально, и это записанное решение, а не пропуск** (`00 §10.1`, принято 2026-08-02).
`MIN_VOTE_WEIGHT` не претендует стоять против цены покупки веса и не будет поднят до неё: вес покупается
за собственный оборот плюс пошлину, потолка у такого числа нет, а видимость защиты хуже её отсутствия.
Самодонат и самоголосование допустимы by design. Приёмку работы здесь удерживает публичность сторон
(репутация обеих публична и линейна), а не цена голоса — и это ровно то, что игра обещает, ни больше.
Деньги при этом охраняет не голосование, а форма — см. ниже. После запуска числа менять дороже:
`voting_period` вшит в прообраз `task_id`, а игра заменяется, а не апгрейдится.

**Чего это не переворачивает.** Ончейн-`refund()` остаётся permissionless после `deadline` и отдаёт 100%
донору (`crown-factory/docs/spec.md` — обязательное требование формы). Перевёрнут **вердикт**, а не
конечный фолбэк: `Settle` реально доходит до получателя, только если тот заклеймит, и окно на это —
`DEADLINE_MARGIN` = 72 ч между `voting_end` и `deadline`. Дальше `claim` и `refund` живы оба, кто успел.
Молчание всей системы (лежащая канистра) по-прежнему возвращает деньги донору.

## Тайминги (якорь на ончейн-`deadline`)

Эскроу `two-outcome` не несёт времени рождения — только `deadline`. Поэтому окна выводятся из `deadline`
как чистая функция `f(голоса, deadline, now)` (без create-clock, без таймера):
- **Отсечка accept/ready** (кэнсел `Created`/`Accepted`): `cutoff = deadline − voting_period − DEADLINE_MARGIN`.
  При `now ≥ cutoff` без `Ready` → `Cancel`.
- **Конец окна голосования** (тали `Voting`): `voting_end = deadline − DEADLINE_MARGIN`.
- `duration` в соль эскроу не входит; его несёт вызывающий + подпись донора и он проверяется лишь
  неравенством дедлайна при регистрации (§Валидация); самим отсечением служит `deadline`.
- `DEADLINE_MARGIN` (72 ч) гарантирует зазор между вердиктом и открытием `refund()`.

## Валидация регистрации (порядок и отказы)

`GrossBelowFloor` (`gross <` игровой флор) → `DurationOutOfRange`
(`duration ∉ [MIN_DURATION, MAX_DURATION]`) → `DeadlineTooTight`
(`deadline < now + duration + voting_period + DEADLINE_MARGIN`; арифметика `checked`, переполнение →
`TimeOverflow`). Граница точная: ровно минимум проходит, минус секунда — отказ.

**Первые два отказа — на границе, третий — в апдейте, и делит их не удобство, а часы** (`P8`,
харнесс §6: «на границе допустим только тот отказ, который время не может отменить»). `gross` и
`duration` коммитятся `task_id` против уже существующего и неизменного эскроу, поэтому отказ по ним
вечен; `deadline` сравнивается с `now`, и время его отменяет. Разделение — `validate_time_free`
(флор + диапазон) внутри `validate_registration`: одна формулировка закона, два вызывающих, согласие
пиннуто тестом по обеим сторонам. Раньше обе клочно-временные проверки жили только в апдейте, и
подфлорная регистрация была **шаблоном флуда**: она не материализуется, значит `is_materialized`
границу за неё не закрывает, а подписанная половина запроса нонса не несёт — одно сообщение
переигрывается вечно и каждый раз исполняется реплицированно. У `conditional-funding` обе проверки на
границе стояли изначально (её `created_at` — из слота рождения, а не из часов).

**Условий получателя здесь нет, и это решение, а не пропуск** (`P7.14`). Регистрация идёт **за пруфом
рождения**: к моменту, когда канистра могла бы отказать, донор уже профинансировал эскроу и оплатил
впись рождения и пуш корня. Отказ в этой точке стоит донору трёх оплаченных шагов и не защищает
никого: ненужное задание отклоняется (`decline`) либо просто игнорируется, и по дедлайну `refund()`
возвращает деньги. Полезен такой фильтр только **до** создания эскроу, то есть в клиенте, — там он и
живёт. Всё, что осталось в списке выше, — платформенные инварианты, а не предпочтения получателя.

## Форматы подписываемых сообщений (замороженный протокол)

`DOMAIN = "crown:conditional-tasks:v1"` — **первая строка сообщения, и она сверяется** (в общем
`crown-games-common::request::parse`, до подписи: сравнение дешевле `verify_strict`). До `P8` не
сверялась ни в одной игре — строка не несёт `": "`, разбор полей её пропускал, а `target_ok` связывал
только `canister`/`chain`, поэтому подпись, взятая под любым другим предлогом, открывала действие
области (разбор — `games-harness.md §7`). Дальше: Ed25519 кошельком (`verify_strict`), адрес ≡ pubkey
(32 б), подпись 64 б. Одно поле на строку, `key: value`, фиксированный порядок; печатный ASCII;
кодирование инъективно (пиннится юнит-тестами).

**Задание:**
```
crown:conditional-tasks:v1
action: <register|accept|decline|ready|vote>
chain: <chain id>
canister: <principal>
task: <bs58(task_id)>
```
`register` добавляет `text: <hex(text_hash)>` и `duration: <dec>`; `vote` добавляет `choice: <done|not_done>`.

**Неподписанные экстры** (после `---`, кроме `pubkey`/`signature`) — то, что вызывающий предъявляет, а
канистра перепроверяет пруфом; авторизацией они не служат. `register`: `recipient`, `gross`, `deadline`,
`nonce`, `witness`; `vote`: `weight_witness`. Экстры пиннуты подписанным `task_id`: подмена любой из них
не сойдётся при пересчёте. **`fee_bps`/`fee_wallet` экстрами не являются и не принимаются** — комиссия
берётся из конфига (харнесс §9).

**Свидетель в регистрации ровно один.** Вторым шёл `rep_witness` — репутация донора, читавшаяся, только
если профиль получателя её требовал. Профиля нет (`P7.14`), и с ним ушёл единственный читатель книги на
пути регистрации: репутация доказывается теперь лишь на голосе. Граница подешевела ровно на один обход
хеш-дерева.

**Вердикт (в `claim`, побайтово, `games-harness.md §5`):**
`verdict_message = "crown:two-outcome:<cluster>" ‖ program_id(32) ‖ u8(outcome) ‖ u16le(fee_bps) ‖ fee_wallet(32)`,
`outcome`: `settle=0`, `cancel=1`. Подпись — `key([task_id])`; проверяется против поля `resolver` эскроу.
Одна подпись на область (при `B=1` — на её единственный эскроу).

`fee_bps`/`fee_wallet` в сообщении — из **конфига игры**, и форма сверяет суффикс с собственными полями
эскроу. `B=1` держится дедупом области, а не устройством формы: резолвер `key([task_id])` выводит кто
угодно, поэтому под областью задания можно родить второй эскроу — со своей комиссией. Пока комиссии в
сообщении не было, подпись задания открывала и его (харнесс §9). Теперь не открывает; такой эскроу
доживает до дедлайна и возвращается донору.

## Условия получателя — в клиенте, не в канистре

Ручек получателя у канистры нет: ни `set_profile`, ни `get_profile`, ни хранимой таблицы. Приём
задания разрешён всегда, а несогласие выражается тем, чем оно и выражалось раньше по существу —
`decline`, либо молчанием до дедлайна, после которого `refund()` возвращает донору всё.

Почему не в канистре — §Валидация регистрации: проверка стоит за пруфом рождения, то есть срабатывает
уже после того, как донор потратился. Почему не «просто с кэпом» — кэп и был экспозицией: таблицу,
писать в которую мог любой свежий ключ, заполняли посторонние, после чего **ни один новый получатель**
не сохранялся уже никогда, на канистре, состояние которой не переносится между версиями (харнесс §7).
Механизм, поставленный против собственного роста, оказался кнопкой необратимого отказа — тот же признак
отбора, что на `P7.7` (`07-build-plan.md`).

Заодно снялось исключение из `00 §11` («ни одного хранимого байта без реального эскроу за спиной»):
`set_profile` был единственной записью без пруфа рождения. Теперь их ноль.

Клиент показывает условия донору **до** создания эскроу и фильтрует ими выдачу получателя. Если
когда-нибудь понадобится доказуемость, получатель сможет подписывать свои условия, а донор —
предъявлять их: это клиентская договорённость, канистры она не касается.

## Терминальные исходы: деньги / комиссия / репутация

| Исход | Деньги | Комиссия | `Settled` | Репутация |
|---|---|---|---|---|
| `settle` (0), `claim(0,sig)` | `fee → fee_wallet`; `splitter.donate(recipient, gross − fee)` | `fee = gross·fee_bps/10000` | `donor = escrow` | **донору**, `= gross − fee` (прошедшее через сплиттер; комиссия в книгу не попадает) |
| `cancel` (1), `claim(1,sig)` | 100% → донор | нет | нет | нет |
| `refund()` (ончейн, кто угодно, строго после `deadline`) | 100% → донор | нет | нет | нет |

Репутация — только донору, только при исполненном `claim(0)`; отказ/таймаут/`refund` не дают ничего.
Заработать больше внесённого нельзя.

## Крайние случаи (обязаны сохраниться)

- Двойной `accept` → `InvalidTransition`, состояние остаётся `Accepted`.
- `decline` из `Created` **и** из `Accepted` → `Cancel`.
- `vote` после конца окна → окно тальится первым, голос отвергнут, вердикт записан.
- Повторный `ready`, `ready`/`vote` из `Created`, `vote` из `Accepted`, любое действие из `Decided` → отказ.
- `accept` в последнюю секунду до `cutoff` — работает; ровно в `cutoff` — уже `Cancel`.
- Дубль голосующего `(task_id, voter)` / вес `< MIN_VOTE_WEIGHT` → отказ, счёт не меняется.
- Дубль `task_id` при регистрации → отказ (материализация идемпотентна).
- Переполнение суммы весов → `Cancel`; переполнение арифметики часов → ошибка, состояние не тронуто.
- Иммутабельность вердикта: исход пишется до первой подписи; ретрай подписывает тот же исход.
- `donor == recipient` — **не блокируется** (как в оригинале; самодонат — принятое ограничение).

## Методы (`.did`, фиксирован)

**Update:** `register_task` · `accept` · `decline` · `ready` · `vote` · `request_signature` ·
**`push_root`** (+ `init`/`bootstrap`).
**Query:** `get_task` · `get_verdict` (`null` до `Decided`) · `get_resolver` · `get_signature` ·
`get_sign_price` · `get_logic_version`.

`set_profile`/`get_profile` в списке нет — условия получателя живут в клиенте (§Условия получателя).

Порядок `vote`: подпись → время(`Tick`) → состояние `Voting` → дедуп `(task_id, voter)` → пруф веса
(локально, `MIN_VOTE_WEIGHT`).

**`get_sign_price()` — свободный `query`: во что обходится подпись сейчас.** Отдаёт `max(`забейканный
`SIGN_PRICE`, цена, которую котирует сам IC для нашего ключа`)`, и это же число гейтит оплату в
`request_signature`. Забейканная цена берётся из `config/` на сборке, а настоящую назначает сеть —
пока константа больше, не меняется ничего; в день, когда сетевая цена её перегонит, игра, продолжающая
брать константу, подписывала бы **в убыток**, и единственным симптомом был бы падающий баланс циклов.
Запрос свободный именно затем, чтобы мониторинг видел сближение двух чисел **до** того, как его увидит
первый расчёт: релейный `sign_price` обязан быть не ниже этого. Забрикетить нельзя — сегодня ответ
равен константе побайтово, а если сетевая цена её перегонит, `request_signature` ответит `Underpaid`
вместо подписи в убыток: это громкий простой, чинимый двумя строками конфига (ни игры, ни релеер не
заморожены), а не тихая утечка. Эскроу это не касается — они возвращаются по дедлайну без подписи вовсе.

**`push_root(cert)` — оплаченный пуш корня индекса** (фронтит релеер за `ROOT_PRICE`). Канистра
аутентифицирует сертификат индекса (две BLS-пары: подпись индекса + делегация сабнета) против NNS
root key и кладёт `combined_root` в кеш `ROOTS` (глубина `ROOT_CACHE = 4`). Дальше **всякий** пруф
рождения/репутации — обход хеш-дерева против любого корня из кеша, без пар.

Зачем расщепление: BLS-пары не влезают в бюджет `inspect_message` (200M инструкций) — прямой ingress
`register_task` с сертификатом отбивается `CanisterInstructionLimitExceeded`, то есть **валидная**
регистрация не проходит вовсе; а бесплатной на `update` эта проверка была бы реплицируемой парой на
любую анонимную строку байт. Платный разовый пуш делает дорогим ровно один шаг и оставляет дешёвыми
все per-caller пути (`cost.md §6` #2). Оплата принимается **до** пар, на кривом сертификате не
возвращается (`01-standards §Тесты 4`). Кеш из нескольких корней нужен потому, что корень индекса
двигается на каждой вписи: свидетель, собранный против актуального на тот момент корня, обязан
пройти, пока не приедет следующий `push_root`. Кеш маленький намеренно — старый корень есть окно, в
котором доказуемо уже исправленное состояние книги. Повторный пуш того же корня освежает позицию, а не
растит кеш (иначе реплей вытеснил бы все живые корни).

**`get_signature(task)`** — свободный `query`: байты уже произведённой подписи вердикта. Тот, кто
проиграл гонку за `request_signature` или кому байты нужны ещё раз, читает их здесь, а не покупает
подпись повторно (`cost.md §6` #5).

**Граница (`inspect_message`, харнесс §6):** каждый меняющий состояние вызов доказывает применимость до
раунда — `register_task` флором и диапазоном `duration` (§Валидация регистрации; **до** деривации
`task_id`, резолвера и обхода дерева — самый дешёвый отказ идёт первым) плюс пруфом рождения
**против кешированного корня** (обход хеш-дерева, O(log n);
BLS сюда не идёт — она на оплаченном `push_root`), `accept`/`decline`/`ready` подписант ≡ получатель +
состояние допускает, `vote` пруф веса + порог. Первым режется размер
аргумента (`MAX_ARG_BYTES = 8 KiB`) — многомегабайтный флуд не заставляет даже парсить. `bootstrap`
допускается только пока мастер-ключ не взят (повтор отбивается бесплатно). `request_signature` и
`push_root` — relay-fronted (inter-canister), границу не проходят; прямой ingress на них не декодируется
как один `text` и отбивается. Обречённое отбивается не-реплицируемо; `update` остаётся авторитетным
(дедуп/кэп/машина состояний).

Query состояния игры **не сертифицированы** (`+witness` снят по всему проекту): доверие в Crown течёт через
threshold-подпись резолвера (проверяется on-chain) и сертифицированные пруфы **индекса** (книга/рождения),
а не через состояние канистры-игры — деньги эскроу клеймит против подписи, не против query. Трастовое чтение
состояния игры, если понадобится, — отдельный версионный метод, не часть замороженного ядра.

Плюс два операционных метода вне пользовательского протокола:
- `init(opt InitArgs{index, nns_root_key})` — конструктор: на testnet override principal индекса + NNS
  root key (PocketIC/тест-IC отличаются от mainnet); на mainnet override **трапает** (пиннутый конфиг +
  IC root key — источник истины). `IC_MAINNET_ROOT_KEY` **вбит** (P8) и живёт одной копией в
  `crown-games-common::birth` — ключ общий с сертификатом замороженного индекса, поэтому разъехавшаяся
  копия молча провалила бы все пруфы этой игры. Тип `&[u8; 133]`: невбитый якорь невыразим, потому
  рантайм-проверки «ключ пустой» здесь нет — гарантию даёт тип, а не трап.
- `bootstrap()` — одноразовый (идемпотентный) фетч мастер-Schnorr-ключа (`schnorr_public_key`) после
  деплоя; `init` синхронен и таймеры запрещены, поэтому кеш ключа заполняется явным setup-вызовом, до
  первого `get_resolver`.

Профили конфига — **два**: `testnet` и `mainnet`. Имя threshold-ключа задаёт **окружение**, а не
профиль: `key_1` — локально (сеть dfx сама работает на PocketIC) и на IC mainnet, `test_key_1` — на
тестовом сабнете IC; оба профиля поэтому несут `key_1`. Стоявший в `testnet.toml` `dfx_test_key` не
заводится ни в одном из трёх — это и был весь «блокер» подписи, а не отсутствие возможности.
Подписывать локально можно и проще всего проверяется так: `dfx deploy` → `dfx canister call
conditional-tasks bootstrap` → `KeyBootstrapped`. Третий профиль (`pocketic`), заведённый под обход
неверного имени, удалён вместе с ним.

## Специфика харденинга (дельты к харнессу)

- **Слепа:** внешние сети не читает; вердикт для несуществующего эскроу безвреден и закрыт гейтом рождения.
- **Ленивое создание:** `register_task` — деривация `task_id`, пишет ноль; запись материализуется на
  первом эскроу с пруфом рождения. Триггер материализации — пруф рождения (не самоподпись). `duration`,
  `text_hash` + Register-подпись донора несёт материализующий вызов. Второго пруфа на этом пути нет:
  репутация донора здесь не читается вовсе (§Условия получателя).
- **Без таймера:** отсечка и конец окна — чистые функции от `deadline` (§Тайминги). Подпись — оплаченный pull.

## DoD / тесты (`crown-spec/docs/01-standards.md §Тесты 8,9,12`)

`logic/` zero-dep, property-тесты: cancel-строго-больше-not_done, ничья→settle, пусто→settle, переполнение→cancel;
`failed_action_is_a_tick`; `decided_is_absorbing`; граница `cutoff`/`voting_end` точная; `Overflow` не
двигает состояние. Слепа (grep сетей пуст). Ленивое создание: без пруфа рождения — ноль записи. Граница:
обречённый вызов (плохой пруф рождения/веса, не тот подписант, пере-кэп) отбит в `inspect_message`, до
реплицируемого `update`; голос — дедуп `(task_id, voter)`. Одна подпись области над
`(DOMAIN‖program‖outcome)`, проверяется против `resolver` эскроу. Форматы сообщений пиннуты. Текст —
только хеш в канистре. Комиссия из конфига: регистрация с `fee_wallet = свой`/`fee_bps = 0` не сходится
в принимаемый `task_id` (`full_e2e`, харнесс §9). E2e через реальную сеть.
