# auction — Спека

Игра класса B на форме `two-outcome`. Получатель открывает аукцион на `duration`. Зрители ставят: каждый
кладёт деньги в **свой** эскроу + прикладывает текст-условие. Текст сначала виден только получателю;
принял (`accept_lot`) — текст раскрыт, лот в торгах; в принятый лот можно **доливать** (новый эскроу к
тому же `text_hash`). Окно закрылось — **побеждает лот с самой большой суммой живых вкладов**; ему
`Settle`, всем остальным `Cancel`. **Лот = конкурсная группа; область расчёта = вклад**
(`resolver = key([entry_id])`).

Победителя **никто не называет**: ни голосование, ни получатель. Закрытие — арифметика, и это
единственное, что решает исход. Дискреция получателя ограничена допуском к конкурсу (`accept_lot`,
`return_lot`, `return_entry`, `cancel_auction`) и вся живёт **до** отсечки `T`.

Общие инварианты — `crown-spec/docs/games-harness.md`; здесь — вся специфика аукциона, дословно.

## Идентификаторы, резолвер, набор эскроу

- `auction_id = sha256("crown:auction" ‖ u8(len(canister_id)) ‖ canister_id ‖ recipient(32) ‖
  u64le(recipient_nonce) ‖ u64le(duration) ‖ u64le(min_entry))` — свободный, конфиг в прообразе.
- **Лот — конкурсная группа**: `lot_id = sha256(auction_id ‖ text_hash)`. По `lot_id` идут `accept_lot`,
  `return_lot`, `return_entry`. Лот **не** несёт резолвера — только группирует вклады с общим условием
  (`text_hash`) для приёма и для сравнения сумм на закрытии.
- **Вклад — единица расчёта**:
  `entry_id = sha256(lot_id ‖ donor(32) ‖ u64le(nonce) ‖ u64le(gross) ‖ i64le(deadline))`,
  `resolver = key([entry_id])`. У каждого эскроу **свой** резолвер. Эскроу транзитивно коммитит к таймингам
  через `resolver → entry_id → lot_id → auction_id`.
  - **`gross` и `deadline` входят в прообраз обязательно** (`games-harness.md §4`: область 1:1 коммитит
    их). Это ровно те два поля, из которых деривится адрес эскроу и которых тройка
    `(lot, donor, nonce)` не содержит. Без них один донор под одним `nonce` фондирует **два** эскроу
    (другая сумма или другой дедлайн — `validate::deadline_ok` ограничивает его только снизу), они
    деривятся в **разные** адреса и потому оба проходят `DuplicateEscrow`, но попадают в **одну**
    область: один резолвер, один мемоизированный вердикт. Тогда `return_entry` по дешёвому близнецу
    даёт подпись `Cancel`, предъявляемую дорогому, — донор забирает деньги после закрытия.
    Цикла деривации это не создаёт: `gross`/`deadline` — поля, предъявляемые вызывающим, и адрес
    зависит от них **через** резолвер, а не наоборот.
- **Почему резолвер на вкладе, а не на лоте.** `return_entry` разводит исходы вкладов одного лота
  (возвращённый → `Cancel`, прочие → исход лота). Общий резолвер лота дал бы **одну** подпись на всех — и
  возвращённый вклад смог бы клеймить `settle` вместе с соседями. Резолвер-на-листе: у каждого эскроу своя
  подпись и свой исход. Цена: подпись **не** амортизируется на лот (каждый эскроу платит за свою). Это
  сознательный размен корректности на стоимость.
- **Набор эскроу на лот** (не один): долив = новое рождение под тот же `text_hash` (свой `entry_id` и
  резолвер), чтобы каждый доливающий получил репутацию за свой вклад. Долив — и единственный способ
  поднять ставку лота: суммы вкладов складываются.

## Состояния

`Bidding` · `Done{winner_lot: opt [u8;32]}`. Два состояния, потому что у аукциона ровно два момента:
окно приёма и его закрытие. `Done{winner_lot=null}` = победителя не было (`cancel_auction`, либо на
закрытии не стояло ни одного пригодного лота).

Единственная временная граница (применяется **до** действия, `checked`):
- `Bidding → Done{winner_lot = top()}` при `now ≥ T`, где `T = created_at + duration`.

`top()` — один проход канистры по лотам: пригодный лот с наибольшей суммой живых вкладов. Пригоден лот
**принятый** (`accepted_at≠null`), **не возвращённый** (`returned=null`) и **с ненулевой суммой**
(`total>0`; принятый лот, все вклады которого возвращены, денег не держит и settle'ить нечего). Ничьи —
лоту, открывшемуся раньше (сравнение строгое, `>`): поздняя ставка обязана перебить, а не сравняться.

`Done` — поглощающее, поэтому победитель фиксируется в момент вычисления и больше не пересчитывается.
Само вычисление ленивое — на первом же вызове после `T`; **от того, кто и когда коснулся аукциона
первым, результат не зависит**: всякое действие, способное двинуть сумму, требует `Bidding`, которое
`now ≥ T` уже покинуло, то есть набор лотов заморожен на `T`.

`created_at` — слот рождения первого подтверждённого вклада (слот→время по линейному якорю
`slot_ms`/`genesis_slot`/`genesis_unix` из `config/`, как в `conditional-funding`), фиксируется при
материализации.

**Лот** (поля, не enum): `accepted_at: opt`, `returned: opt`, `text_hash`, `total: u128`, вклады. Роли:
незарегистрирован · зарегистрирован-непринят · принят (`accepted_at≠null`) · возвращён (`returned≠null`) ·
победитель (`Done.winner_lot == lot_id`). Побеждать может только пригодный лот — принятый, не
возвращённый и с `total>0`.

**Вклад:** `returned: opt`, `gross: u64`, `escrow`, `entry_id`.

## Таблица переходов

Время применяется первым; провалившееся из-за сдвига времени действие всё равно персистит наступивший переход.

| Метод | Bidding (`now < T`) | Done (в т.ч. `now ≥ T`) |
|---|---|---|
| `get_resolver` | OK (query, в любом состоянии) | |
| `register_entry` | OK (`gross≥min_entry`, `deadline≥floor`, лот не возвращён, пруф рождения) | ✗ |
| `accept_lot` | OK (лот есть, не принят, не возвращён) | ✗ |
| `return_lot` | OK → лот `returned`, из конкурса выбывает | ✗ |
| `return_entry` | OK → вклад `returned`, его `gross` уходит из суммы лота | ✗ |
| `cancel_auction` | OK → `Done{null}` | ✗ |
| `request_signature` | по `resolve`: возвращённый вклад/лот → `Cancel`; иначе «нет вердикта» | по `resolve` |

Всё, чем получатель управляет конкурсом, живёт **до** `T`. На `T` окно захлопывается само, победитель
вычисляется, и `Done` больше ничего не принимает — отменить или «выкурировать» неудобный исход задним
числом нельзя. Гонка `cancel_auction` с закрытием проигрывает по построению: время применяется первым.

Ленивое создание: `auction_id` — чистая деривация, её считает **клиент**; материализация происходит на
**первом подтверждённом вкладе**, где хеш-проверяются `duration`/`min_entry` из прообраза и валидируется
диапазон (`[MIN_DURATION,MAX_DURATION]`). Первое касание канистры — сразу `register_entry` с пруфом
рождения, ровно как у эталона (`conditional-tasks`).

**Метода-эха `get_auction_id` больше нет, и это правка аудита — по минимализму, не по стоимости.**
`P7.15` увёл его из `update` в `query`, и на этом вопрос цены закрылся: чтение стоит `$0`
(`cost.md §1`), так что жечь им было нечего. Осталась причина из `CLAUDE.md §Минимализм: у каждой
строки — текущий потребитель`. Потребителя не было ни одного — ни тест, ни `full_e2e`, ни драйвер `A5`
его не звали: `auction_id` это `sha256` от полей, которые вызывающий сам и предъявляет, а подпись,
которую метод проверял, ничего не добавляла (свежий ключ подписывает своё же сообщение). Эталон
(`conditional-tasks`) такого метода не имеет вовсе. Удалён вместе с `create_message` и вариантом
`Derived`. Контроль получателя (`accept`/`return_lot`/`return_entry`/`cancel`) — signature-gated по
`recipient` из прообраза; `cancel_auction` самоподписан, пруфа рождения не несёт и **не** материализует.

## Победитель: закрытие вместо решения

Побеждает **самая дорогая ставка**, и решает это одна арифметика:

`winner_lot = argmax_{лот пригоден} total(лот)`, `total(лот) = Σ gross живых вкладов`.

Ни голосования, ни `pick_winner` в системе нет. Что осталось у получателя — допуск к конкурсу
(`accept_lot`), исключение лота (`return_lot`) и исключение отдельного вклада (`return_entry`), и всё
это **до** `T`. Курирование сдвигает множество, по которому считается максимум, но не сам критерий:
среди допущенных всегда выигрывает тот, кто поставил больше.

**Граница гарантии, дословно (вход аудита).** Курирование живёт до самого `T`, поэтому получатель может
за секунду до закрытия вернуть лидера — и закрытие достанется второму. Формально это позволяет выбрать
победителя среди стоящих лотов, то есть гарантия читается как «самая дорогая ставка **из допущенных
получателем**», а не «самая дорогая вообще». Разница с прежним `pick_winner` при этом существенная и не
косметическая: **такой ход теперь стоит получателю денег.** Вернув лидера, он получает не `top−fee`, а
`second−fee`; выбор победителя из бесплатного стал платным ровно на разницу ставок. Стимул выровнен:
единственная причина отвергнуть лидера — неприемлемое текст-условие, для чего курирование и существует.
Жёстче это закрывалось бы только заморозкой курирования за какое-то время **до** `T` — то есть вторым
временным окном, которого в игре сознательно нет.

**Канистра перестала быть слепой к суммам, и это обязательное следствие правила.** `gross`
подтверждённого вклада хранится, у лота — инкрементальный `total` (прибавка на подтверждённом вкладе,
вычитание на `return_entry`), поэтому стояние читается бесплатно, а закрытие — один проход по лотам,
а не по всем вкладам. Пагинации, курсора и таймера по-прежнему нет.

**Почему заявленному `gross` можно верить без чтения чейна.** `gross` входит в соль адреса эскроу
(`crown-salt::two_outcome`), а индекс выдаёт рождение только для `create_escrow`, сверенного с
исполненным `TransferChecked` — тот же `mint` (usdc), `amount == gross`, `authority == donor`
(`crown-indexer/src/recognize.rs`). Соврать в `gross` значит вывести адрес, по которому рождения нет, и
`register_entry` отобьётся на пруфе. То есть сумма в `total` — это ровно те деньги, что лежат в vault'е.

**Ничьи — лоту, открывшемуся раньше.** Сравнение строгое, порядок — по появлению первого
подтверждённого вклада лота. Это правило нужно не для эстетики: без него исход зависел бы от порядка
обхода структуры.

## Трёхступенчатое разрешение (`request_signature`, per-entry)

`request_signature(chain, auction, lot, escrow)` разрешает **конкретный вклад** (по его `escrow`) и
подписывает вердикт ключом `key([entry_id])` этого вклада:

1. вклад известен и `returned≠null` → `Cancel`;
2. иначе лот известен и `returned≠null` → `Cancel`;
3. иначе, `winner = (Done.winner_lot == lot_id)`:
   - `Done`: победитель→`Settle`; иначе→`Cancel` (в т.ч. когда победителя нет вовсе);
   - `Bidding`: «нет вердикта» (окно ещё открыто, стояние может двинуться).

**Порядок ступеней — не украшение: состояние это ступень 3, а не гейт перед ступенями 1–2.** Возвращённый
вклад и возвращённый лот уже терминальны и неизменны — обратной дороги нет, и победителем такой лот стать
не может, — значит их `Cancel` доступен в момент возврата, а не на закрытии. Аудит нашёл, что канистра
короткозамыкала `Bidding` **до** `resolve`, и лот, отвергнутый получателем на первый день тридцатидневного
аукциона, не мог вернуть деньги до конца месяца: средства доноров стояли за уже принятым решением.
Исправлено — `resolve` зовётся всегда. Перевернуть вердикт это не может: у возвращённого исход `Cancel`
и до, и после закрытия.

Незнакомый вклад (`entry=null`) разрешается только ступенью 3 (`Cancel`, т.к. его лот не победитель).
Ретрай пере-подписывает тот же вердикт. Оплаченный pull: оплата принимается только когда есть вердикт
(не «нет вердикта»), до `sign_with_schnorr`. Победитель берётся из состояния, которое этот же вызов
только что продвинул, — `Done` поглощающее, значит под конкурентным клеймом он не сдвинется.

## Двухступенчатый борд

- **«заявлено»** — пруф истории кошелька; проверяется бесплатно; на доску сразу; **вне канистры** (слой
  `crown-app`, в периметре не хранится); на исход **не влияет**.
- **«подтверждено»** — пруф рождения эскроу; только подтверждённые вклады существуют для канистры и
  только они входят в `total`. `register_entry` не читает чейн → **пруф рождения** (свидетель против
  корня рождений, локально).
- Пруф несёт **слот рождения** → подтвердить можно задним числом в окне приёма. **Отсечка `T`**:
  `T = created_at + duration` — граница приёма (`register_entry` при `now ≥ T` отбит: аукцион уже
  `Done`). Пруф вклада засчитывается, только если подан до `T`. Внешняя граница жизни эскроу —
  `deadline`. Пруф доказывает факт рождения, **не** live-`closed`; на мёртвость/возврат полагаемся
  через `deadline`/`refund()`, а не live-чтение (его нет).

С арифметическим победителем борд стал ещё важнее как UI: `get_lot` отдаёт `total` лота — донор,
решающий доливать ли, обязан видеть стояние, против которого ставит, и видит **число канистры**, а не
реконструкцию борда.

## Правило дедлайна

`deadline ≥ created_at + duration + DEADLINE_MARGIN`; все сложения `checked`, переполнение → ошибка
(не пропуск); граница включительна. Проверяется при `register_entry`. Жизненный цикл кончается на
закрытии (`created_at + duration`), поэтому маржа — это ровно то время, которое есть у клеймера,
чтобы предъявить вердикт ончейн до открытия `refund()`.

## Константы

| Константа | Значение |
|---|---|
| `MIN_DURATION` | `60` (1 мин) |
| `MAX_DURATION` | `2_592_000` (30 сут) |
| `DEADLINE_MARGIN` | `259_200` (72 ч) |
| `LOGIC_VERSION` | `2` (арифметическое закрытие вместо голосования и `pick_winner`); пиннуется тестом на неизменность |
| `min_entry` | поле прообраза (создатель) — может флор только **поднять**. Платформенный флор — `config::MIN_ENTRY` = `2_200_000`; эффективный = `max(min_entry, MIN_ENTRY)` (`validate::entry_floor`). Резолвер здесь **на вкладе** (`key([entry_id])`), поэтому каждый вклад покупает свою подпись и амортизировать её нечем — флор равен эталонному `be·(1+MARGIN)` задания ($2.20 на измеренных ценах `P7.22`, `cost.md §5,§6`), а не амортизированному. Дефолт `0` был дырой: создатель обнулял флор и платформа платила подпись за пыль. Алайнмент с индексным `MIN_GROSS` — шаг cost-gate на P8, **не тест** (снят на `P7.13`: сравнивал чужой флор с литералом-копией и покраснеть при его подъёме не мог — разбор в `canister/src/config.rs`); итоговое число — тоже выход cost-gate на P8 |
| `duration` | поле прообраза, диапазон `[MIN_DURATION, MAX_DURATION]` |
| `MAX_ARG_BYTES` | `8 KiB` — кэп аргумента ingress, режется первым; выведен из ёмкости поколения, не выбран (харнесс §6) |
| `sign_price` | `26.2e9` (devnet), ≤ релейного `SIGN_PRICE` |
| `slot_ms`/`genesis_slot`/`genesis_unix` | якорь слот→время для `created_at` (как в `conditional-funding`); devnet-якорь **замерен** на A5, mainnet — плейсхолдер до P8 (фриз-гейт `genesis_unix≠0`). Модель линейна по `slot_ms`, сеть идёт чуть быстрее — `created_at` уползает **вперёд**, то есть окно приёма шире, а не уже; дрейф проверяет A5-драйвер до движения денег |

`MIN_VOTE_WEIGHT`, `V_MAX`, `voting_period`, `perform_window` в аукционе **отсутствуют** — вместе с
голосованием и стадией выполнения. `V_MAX`/`MIN_VOTE_WEIGHT` остаются в глоссарии и в
`crown-games-common` для игр, где голос есть.

## Вердикт-сообщение и деньги

**Подпись вклада** `key([entry_id])` над
`"crown:two-outcome:<cluster>" ‖ program_id(32) ‖ u8(outcome) ‖ u16le(fee_bps) ‖ fee_wallet(32)`
(комиссия — из конфига игры, харнесс §9)
(`settle=0, cancel=1`); проверяется on-chain против поля `resolver` эскроу. Одна подпись — один вклад
(без корня/пути). Разные вклады лота (в т.ч. возвращённые) подписываются независимо.

`Settle` (0): эскроу → комиссия `fee_bps` → `fee_wallet`; `gross−fee` → получатель; `Settled(donor=escrow)`;
репутация донору = `gross−fee`. Только здесь. `Cancel` (1): 100% донору, ни `Settled`/комиссии/репутации.
`refund()` после `deadline`: донору, без подписи, мимо книги.

## Методы (`.did`, фиксирован)

**Update:** `register_entry` · `accept_lot` · `return_lot` · `return_entry` · `cancel_auction` ·
`request_signature(chain, auction, lot, escrow)` · **`push_root`**.
**Query:** `get_auction` · `get_lot` · `get_resolver` · `get_signature(auction, lot, escrow)` ·
`get_logic_version`. **Инфра:** `init(opt InitArgs)` / `bootstrap()`.

`create_auction`/`get_auction_id` в списке нет — `auction_id` выводит клиент (§Таблица переходов).
`pick_winner`, `ready` и `vote` **удалены**: победителя даёт закрытие, стадии выполнения нет, голоса нет.

`get_resolver(lot, donor, nonce, gross, deadline)` считает `entry_id` (§Идентификаторы) и возвращает
`key([entry_id])`. `gross`/`deadline` — аргументы, потому что область их коммитит; донор их и так знает,
это его собственный эскроу. `get_lot` отдаёт `(accepted, returned, live_entries, total, text_hash)` —
`total` здесь потому, что победитель арифметический и стояние обязано быть читаемым. `get_auction` в
`Bidding` отдаёт **`closes_at`** — это тоже правка аудита: `created_at` фиксирует слот рождения того,
кто зарегистрировался первым, поэтому объявленный получателем `duration` **не** говорит донору, сколько
осталось, а на арифметическом закрытии именно это число решает, успеет ли долив. Без него ставка
делалась вслепую. `get_signature` — свободный `query`: подпись вклада, уже произведённая; проигравший
гонку клеймер читает байты здесь вместо повторного платного pull'а.

**`push_root(cert)` — оплаченный пуш корня индекса** (фронтит релеер за `ROOT_PRICE`). Канистра
аутентифицирует сертификат индекса (две BLS-пары: подпись индекса + делегация сабнета) против NNS
root key и кладёт `combined_root` в кеш `ROOTS` (глубина `ROOT_CACHE = 4`). Дальше **всякий** пруф
рождения — обход хеш-дерева против любого корня из кеша, без пар.

Зачем расщепление: BLS-пары не влезают в бюджет `inspect_message` (200M инструкций) — прямой ingress
`register_entry` с сертификатом отбивался бы `CanisterInstructionLimitExceeded`, то есть **валидная**
регистрация вклада не проходит вовсе; а бесплатной на `update` эта проверка была бы реплицируемой парой
на любую анонимную строку байт. Платный разовый пуш делает дорогим ровно один шаг и оставляет дешёвыми
все per-caller пути (`cost.md §6` #2). Оплата принимается **до** пар, на кривом сертификате не
возвращается (`01-standards §Тесты 4`). Кеш из нескольких корней нужен потому, что корень индекса
двигается на каждой вписи: свидетель, собранный против актуального на тот момент корня, обязан
пройти, пока не приедет следующий `push_root`. Повторный пуш того же корня освежает позицию, а не
растит кеш. Полностью совпадает с эталоном (`conditional-tasks`) — это инвариант харнесса, а не
деталь одной игры. Пруф **веса** с этого пути ушёл вместе с голосом; кеш остался ради пруфа рождения.

**Граница (`inspect_message`, харнесс §6):** каждый меняющий состояние вызов доказывает применимость до
раунда — `register_entry` пруфом рождения **против кешированного корня** (обход хеш-дерева, O(log n);
BLS сюда не идёт — она на оплаченном `push_root`), действия получателя
(`accept_lot`/`return_lot`/`return_entry`/`cancel_auction`) — подписант ≡ получатель + состояние
допускает. Проверка «состояние допускает» не параметризована видом действия: с арифметическим
победителем все действия получателя живут в `Bidding` и ни одно не переживает закрытия, так что эту
половину решает одно состояние.

**Вторая половина — цель действия, и её добавил аудит.** Подписанная часть запроса не несёт ни нонса, ни
срока годности, поэтому **любой** однажды увиденный `accept_lot`/`return_lot`/`return_entry` — шаблон,
который кто угодно шлёт заново сколько угодно раз. Пока граница читала только состояние, каждый такой
повтор проходил и исполнялся реплицированно: отправителю бесплатно, канистре — полная проверка подписи и
раунд. Теперь граница читает и **монотонный** факт о цели: лот уже принят (`accept`), лот уже возвращён
(`return_lot`), вклад уже возвращён (`return_entry`). Монотонность здесь — всё требование: `accepted_at`
и `returned` ходят только `None → Some`, значит отказ на границе останется отказом и в раунде. Факты,
способные **появиться** между границей и исполнением (неизвестный лот, неизвестный вклад), сознательно
не читаются — иначе регистрация, приехавшая в том же раунде, делала бы валидный вызов отброшенным.

**У `register_entry` тот же повтор был опаснее всех, и он закрыт.** Обречённая регистрация (аукцион
закрыт, лот возвращён) оставляет свой эскроу **неизвестным**, поэтому `DuplicateEscrow` её повтор не
ловил никогда: одна валидная, birth-пруфнутая заявка — и её можно слать вечно, покупая на каждый повтор
проверку подписи, деривацию резолвера, перебор bump'а PDA и обход хеш-дерева **на каждом узле**. Теперь
состояние аукциона и `returned` лота проверяются сразу после `lot_id` (один sha256) — **до** всей
дорогой деривации, ровно по правилу «самая дешёвая решающая проверка первой» (`cost.md §6` #2). Первым режется размер аргумента (`MAX_ARG_BYTES = 8 KiB`). `bootstrap` допускается
только пока мастер-ключ не взят. `request_signature` и `push_root` — relay-fronted (inter-canister),
границу не проходят; прямой ingress на них не декодируется как один `text` и отбивается. Обречённое
отбивается не-реплицируемо; `update` авторитетен.

Query состояния игры **не сертифицированы** (`+witness` снят): доверие в Crown течёт через threshold-подпись
резолвера (проверяется on-chain) и сертифицированные пруфы **индекса** (книга/рождения), а не через состояние
канистры-игры — деньги эскроу клеймит против подписи, не против query.

## Крайние случаи

- `accept` уже принятого → ✗. `return_lot`/`return_entry` — только в `Bidding`; после `T` состояние
  `Done`, и ни одно действие получателя уже не проходит.
- Долив в непринятый лот разрешён (непринятый не может победить, но может быть принят позже); долив в
  возвращённый лот → ✗. Дубль-эскроу → ✗ (иначе один депозит считался бы в `total` дважды).
- Принятый лот, все вклады которого возвращены (`total = 0`), победить не может — settle'ить нечего.
- Ни одного пригодного лота на закрытии → `Done{null}`, всем `Cancel`. `cancel_auction` до `T` — то же
  самое, немедленно.
- Победитель, вклады которого частично возвращены (`return_entry`): каждый возвращённый вклад лично
  разрешается `Cancel` (ступень 1) и не считается в `total`, живые — исходом лота. Именно ради этого
  резолвер на вкладе.
- Ничья двух пригодных лотов → побеждает открывшийся раньше.
- Escrow, рождённый до `T`, но пруф подан позже (в окне) — засчитывается; после `T` — нет (`refund()`).
- Непруфнутый/незнакомый escrow: ступень 3 (`Cancel` как непобедитель) либо `refund()`.
- «заявлено» никогда не влияет на исход — только «подтверждённые» (пруф рождения) до `T`.
- Возвращённый вклад/лот получает `Cancel` **сразу**, не дожидаясь `T` (§Трёхступенчатое разрешение).
- Отсечку `T` задаёт слот рождения **первого** подтверждённого вклада, а не публикация аукциона: тот,
  кто регистрируется первым старым рождением, укорачивает окно. Материализовать уже закрытый аукцион
  нельзя (гейт `now ≥ created_at + duration` в `register_entry`), а всем прочим фактическое `T` видно в
  `get_auction` (`closes_at`). Полный запрет требовал бы верхней границы на возраст рождения — то есть
  ещё одного окна.

## DoD / тесты (`crown-spec/docs/01-standards.md §Тесты 8,9,12`)

`logic/` zero-dep: машина `Bidding→Done` (граница окна точная, `Overflow` не двигает состояние, `Done`
поглощающее, `cancel` после `T` не отменяет закрытия, `top` не вызывается при открытом окне, победитель
фиксируется один раз и не пересчитывается), правило дедлайна (checked, включительна), трёхступенчатое
разрешение `resolve` per-entry. Не читает сети (grep).

Канистра: `register_entry` — пруф рождения, не RPC; без пруфа ноль записи; приём заморожен на `T`.
**Победитель — самая дорогая ставка:** сумма лота складывается из доливов; непринятый лот не побеждает
никогда; возврат лидера отдаёт закрытие второму; возвращённый вклад уходит из суммы и может перевернуть
исход; опустошённый лот не побеждает; ничья — раньше открывшемуся; закрытие не зависит от того, кто
коснулся аукциона первым после `T`; ни одно действие получателя не проходит после закрытия. Подпись
`key([entry_id])` против `resolver` эскроу; возвращённый вклад лота разрешается `Cancel` независимо.
Граница: обречённый вызов отбит в `inspect_message`, до реплицируемого `update` — плохой пруф рождения,
не тот подписант, закрытый аукцион, **и повтор уже применённого действия** (лот принят / лот возвращён /
вклад возвращён / регистрация в закрытый аукцион или возвращённый лот); при этом граница **не** отказывает
по фактам, способным появиться позже (неизвестный лот/вклад) — иначе валидный вызов терялся бы бесплатно.
Удалённых методов (`vote`/`pick_winner`/`ready`/`get_auction_id`) на канистре нет вовсе. E2e через
реальную сеть: две настоящие ставки разного размера, побеждает бо́льшая.
